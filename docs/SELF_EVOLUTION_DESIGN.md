# WodeAppX 自进化（Self-Evolution）设计方案

> **Last updated:** 2026-07-31
> **状态：** 设计草案；M1 安全底线已落地；安装包内嵌筛选源码已接线
> **范围：** 用户与运行中的WodeAppX / WodeAppX 对话 → Agent 修改自身源码 → 构建新版本 → 安全切换 / 回滚 的完整闭环

---

## 1. 目标与非目标

### 目标

1. 用户在对话中提出"改你自己的某个功能 / 界面"，Agent 直接修改 `wodeappx/` 源码。
2. 改动经过**自动验证**（typecheck / 测试 / 冒烟），失败自动回滚，不留坏代码。
3. 验证通过后构建出新版本 B，与正在运行的版本 A **共存**；切换时不杀当前 Agent 进程、不丢会话。
4. 新版本出问题可**一键回滚**到上一版本。

### 非目标（本期不做）

- 不追求 7×24 无人值守全自动：改代码、构建、切换均保留**用户确认门槛**。
- 不改 OpenWork 会话主链路（遵守 `ARCHITECTURE.md` 的集成边界）。
- 不做远程分发 / 自动更新服务器（属于 release 流程，见 `docs/RELEASE.md`）。
- 不做外观「主题引擎 / 运行时 pack 配置中心」；先提供可复制示例见 [`examples/skin-theme-evolve-examples.md`](examples/skin-theme-evolve-examples.md)。皮肤商店 / 用户互通属后续流通层，仍以自进化改源码 + 对比度门禁为准。

### 1.1 安装包内的可改源码（已落地方向）

打包时由 `wodeappx/scripts/pack-self-evolve-source.mjs` 生成**筛选 monorepo**（开源核目录 + OSS strip，去掉 `vendor`/`node_modules`/大媒体）。  
装包首启解压到 `userData/self-evolve-source/<version>/wodeapp`，侧栏「项目」挂载为 `wodeapp（自进化）`。  
不扫 `~/Desktop/wodeapp`；可用 `WODEAPP_MONOREPO_ROOT` 覆盖。

## 2. 核心思路：A/B 双版本 + 独立 Supervisor

Agent 住在版本 A 进程里，任何"重启自己"的方案都会杀掉自己。解法是 Agent 只负责**改代码、验证、构建、申请切换**，版本切换由不属于任何版本的轻量 **Supervisor** 执行：

```text
┌────────────────────────────────────────────────────────┐
│ Supervisor（独立于任何版本，极薄，只管指针与进程）         │
│   versions/current -> 指向 A 或 B                       │
│   职责：启动候选版本、健康检查、切指针、回滚               │
└────────────────────────────────────────────────────────┘
        ▲ 申请切换 / 回滚                    ▲ 启动 / 探活
        │                                  │
┌───────┴──────────┐           ┌───────────┴──────────┐
│ 版本 A（运行中）   │           │ 版本 B（候选）         │
│ Agent 住在这里    │  构建→    │ 独立构建产物目录        │
│ 改代码/验证/构建  │  验证    │ 健康检查通过后才切换     │
└──────────────────┘           └──────────────────────┘
        └────── 共享同一份 runtime-data（会话 / 配置 / 工作区状态）──────┘
```

关键性质：

- **Agent 永远不被杀**：切换只是"下次启动走 B"，A 优雅退出或暂时保留。
- **天然带回滚**：B 不健康就不切；切换后发现问题是 B 引入的，指针切回 A 即可。
- **会话连续**：A/B 共享同一账号的 `openwork-runtime-data/<accountId>`，B 启动即读到对话历史，用户无感。

### 2.1 版本管理：本地影子 git 仓库（不内置 Gitea）

**决策：用本地 git 做版本管理，不默认内置 Gitea。** 理由：

| 候选 | 结论 | 原因 |
|------|------|------|
| 本地 git 影子仓库 | **采用** | git 本身就是完整版本系统（commit/log/diff/restore 全有）；零新依赖、零常驻进程，符合 Supervisor 最小化原则 |
| 内置 Gitea | 不采用（后期可选） | 桌面端单用户场景不需要常驻服务端 + 数据库 + Web UI；维护成本高。其价值在多机同步 / 团队审阅，可作为影子仓库的远程 remote 后期接入，不影响本地闭环 |

**实现**（已落地，`scripts/self-evolve-guard.mjs version *`）：

```text
影子仓库：~/.wodeappx/self-evolve/repo.git（bare）
GIT_WORK_TREE = wodeappx 根目录
  · 与外层业务仓库完全隔离（wodeappx 不是独立 git 仓库，外层仓库历史不受污染）
  · 被外层 gitignore 的 vendor/openwork 源码通过 git add -f + 显式纳管清单纳入版本
  · 纳管清单（VERSION_INCLUDE）只含源码；node_modules / dist / target / 二进制资源排除
```

- `version commit --label "<说明>"`：验证通过且用户确认生效后，切一个命名版本（首次约 2500 文件 / 3 秒）。
- `version log`：版本历史。
- `version restore <hash>`：回退到任意历史版本。**追加式提交**（`restore to <hash>: <原label>`），不改写历史，回退本身也可再回退。有未提交变化时拒绝执行，须先 commit 或人工 `--force`。
- 与 M1 快照的关系：snapshot/rollback 管"一次改动过程内"的安全（分钟级、工作区级）；version 管"跨改动"的正式版本史（天/周级、可命名可审计）。rollback 失败或需跨多次改动回退时，用 version restore。
- 与 Phase 2 的衔接：A/B 槽位的构建产物以 version commit hash 命名，`history.json` 记录 `槽位 <-> version hash`，实现"源码版本 ↔ 构建产物 ↔ 运行实例"三者对齐，回退任一层都能找到另外两层。

**已知陷阱（实测踩出）**：guard 脚本自身也在版本域内——`version restore` 回退旧版本会**把工具自己一并回退**。回退后如需继续操作版本库，先从目标/最新版本取回 guard 脚本（`git restore --source <newest> --worktree -- scripts/self-evolve-guard.mjs`）再执行后续命令。

## 4. 分阶段实施

### Phase 1 — 安全底线（先做，独立于 A/B 架构）

目标：让"Agent 改自己代码"这件事**改不坏**。

1. **改动前快照**：自我修改开始前自动 `git status` 检查；有无关改动时提示用户并保留；然后打一个带时间戳的本地快照（临时分支 commit 或 `git stash push`），快照即回滚单位。
2. **改动后验证门禁**（固定流水线）：
   - `pnpm typecheck`（必须过）
   - 受影响包的相关测试（必须过）
   - 涉及 Electron 主进程 / OpenCode sidecar 时，加跑 `scripts/release-preflight.mjs` 的适用子集
3. **失败自动回滚**：任一门禁失败 → 恢复到快照 → 在会话里向用户报告失败原因与"已回滚"的事实。
4. **确认门槛**：
   - 动手改之前：向用户复述改动方案，等确认。
   - 验证通过要"生效"时：再确认一次。Phase 1 阶段 = 用户手动重启或手动跑 dev 生效；Phase 2 之后 = 触发 A/B 切换。

产出物：固化在 Skill / command 里的标准工作流（放 `.opencode/` 或 skills 目录），Agent 每次自我修改都走同一路径，不允许绕过门禁。

> 说明：开发模式下大部分渲染层改动可靠 Vite 热更新即时生效，无需构建与切换。Phase 1 + dev 模式即可覆盖"改 UI / 业务页"的高频场景，是投入产出比最高的第一步。

### Phase 2 — A/B 版本与 Supervisor

1. **版本目录布局**（安装版形态）：

```text
~/.wodeappx/versions/
  a/            # 版本 A 完整构建产物
  b/            # 版本 B 完整构建产物
  current       # 文本文件或 symlink，内容为 a 或 b
  history.json  # 切换历史：{from, to, at, reason, gitCommit}
```

2. **Supervisor**：一个极薄的独立入口（shell 脚本 / launchd 托管的小进程），不属于任何版本。职责只有四个：
   - 读 `current`，启动对应版本；
   - 收到"启动候选"请求时，以**隔离参数**（见 Phase 3）启动另一槽位的版本；
   - 健康检查（见 §5）通过后改写 `current` 并记录 `history.json`；
   - 收到"回滚"或健康检查失败时，指针回到上一槽位。

   Supervisor 自身**几乎不变**，不参与业务，因此不存在"谁更新 Supervisor"的递归问题；真要更新它，走人工 / release 流程。

3. **会话与工作区交接**：A/B 共用同一账号的 `openwork-runtime-data/<accountId>`。约束：会话 / 配置的存储 schema 变更必须**向后兼容**（旧版本能读新数据），否则回滚后 A 起不来。schema 破坏性变更的自进化改动应被验证门禁直接拒绝或要求人工处理。

4. **切换时序**：

```text
A 运行中（Agent 在内）
  → Agent 完成 Phase 1 验证，构建出版本 B 到另一槽位
  → 用户确认"切换到新版本"
  → Agent 请求 Supervisor：启动 B（隔离模式）
  → Supervisor 健康检查 B
      失败 → 杀掉 B，报告原因，A 不动
      成功 → 改写 current → 提示用户"新版本已就绪"
  → A 由用户手动关闭，或 Supervisor 在 B 稳定 N 分钟后优雅结束 A
  → 下次启动（或立即打开的 B 窗口）即为新版本，会话从共享数据恢复
```

### Phase 3 — 资源隔离（默认基础隔离，风险告知不强制）

**原则（2026-07-29 定调）**：不做硬性限制。平台只提供**基础默认隔离**（独立数据目录 / 端口 / 应用标识），其余冲突风险如实告知，由用户自行判断是否接受；想要更严格的互斥策略，用户自己通过自进化流程改代码即可。

**已落地的最小实现**：`scripts/self-evolve-instance.mjs`（start / status / stop）。候选实例默认获得：

- 独立数据目录 `~/.wodeappx/instances/candidate-<id>/user-data`（全新环境，需重新登录；想用正式数据就共用主数据目录，自己改脚本）
- 独立应用标识 `com.differentai.openwork.candidate.<id>`（macOS 授权按标识授予，不影响主 App）
- 独立 CDP 端口 `9222+<id>`（供 A 测 B 自动化，见 §5.1）

**风险告知清单**（不做强制，用户自行判断）：

| 资源 | 共存时可能的问题 | 平台默认 | 用户可选 |
|------|------|------|------|
| 本地端口（OpenWork server / sidecar） | 双实例抢同一端口 | 独立 CDP 端口；server 端口冲突时按日志提示调整 | 改脚本注入偏移端口 |
| 云端账号 / 积分 / 推送 | 同一账号副作用翻倍（重复扣费、重复推送） | **不限制**：候选实例默认可连云端 | 挂独立数据目录（默认即如此）或只读验收 |
| MCP / 辅助进程 | 双实例各 spawn 一套，孤儿进程问题放大（见 `RUNTIME_PERFORMANCE_REMEDIATION.md`） | 不限制 | 用完即 `stop` |
| 系统级授权（Accessibility / 录屏 / Chrome Apple Events） | 授权按 App 标识授予，候选实例可能需重新授权 | 独立标识，授权互不影响 | — |
| Chrome / Computer Use | 两个实例抢同一个浏览器、同一个鼠标键盘 | 不限制 | 自己判断，必要时只用一边 |
| 正式数据共享 | 双实例写同一份 SQLite 可能竞争；两边同时操作同一会话会串状态 | 候选实例默认独立数据目录，天然规避 | 想共享正式数据自己改 `userDataDir` 指向 |

## 5. 健康检查定义

候选版本 B 只有通过以下检查才允许切换：

1. 进程存活 ≥ 60 秒且无 crash report；
2. OpenWork server / OpenCode sidecar 正常应答（本地探活端点 200）；
3. 渲染层加载成功（无白屏，启动日志无 fatal）；
4. 会话列表可读（验证共享 runtime-data 兼容性）；
5. （可选）冒烟工具调用一次：例如 `agent_reach_status` 或一个无副作用的内置工具返回正常。

任一失败 → B 标记为坏版本，指针不动，自动回报日志摘要。

### 5.1 A/B 互相测试（A 测 B，推荐纳入 Phase 2）

用户提问："A、B 之间可以互相测试吗？"——可以，而且这应该是 B 上线前的标准动作。但要区分两个方向的价值：

| 方向 | 价值 | 做法 |
|------|------|------|
| **A 测 B**（住在 A 里的 Agent 驱动候选 B 做测试） | 高。B 上线前的行为级验收，远超"进程活着"的探活 | A 中的 Agent 以 CDP 连接候选 B 实例，跑冒烟/回归场景：会话可读写、关键页面可打开、内置工具可调用。判定结果自动写回切换决策 |
| **B 测 A** | 低。A 是已知好版本，不需要被 B 验证 | 真正的用法是 **A 当回归基线**：同一套测试脚本先后跑在 A 和 B 上，diff 行为差异；只有"B 有、A 无"的预期差异才允许存在，其余差异视为 B 的回归 |

现有基础（不需要从零造）：

- `scripts/wodeappx-test-instances.mjs` 已实现**多实例共存**的核心模式：每实例独立 `user-data` 目录、独立 CDP 端口（9222+实例号）、独立 bundle identifier。该脚本的 `start`/`seed` 当前处于禁用状态（"测试实例已全部禁用；请直接使用开发版"），Phase 2 可复活并改造为"A/B 槽位实例"。
- 开发版 CDP 驱动模式已在 skill `wodeappx-product-video-e2e` 中验证（`http://127.0.0.1:9823`，含会话锁定、主聊天区判读等防串扰规则），同一套 CDP 驱动代码可直接复用于"测 B"。
- 注意：A 测 B 时**必须用 B 独立的 user-data**（test-instances 模式），不能让 B 直接挂共享的正式账号数据跑破坏性场景；会话连续性验收（读共享数据）单独用只读场景跑。

切换决策升级：B 通过 §5 的探活性健康检查后，再由 A 中的 Agent 跑 CDP 行为测试，**两者都过**才允许改写 `current` 指针。行为测试失败 = 健康检查失败，走同一回滚路径。

## 6. 安全与边界

- **确认门槛不省略**：改代码前确认方案；切换版本前再确认。Agent 不得自行完成"改 → 构建 → 切换"全链路无确认。
- **回滚优先**：任何一步失败，默认动作是回到上一个已知好状态，而不是就地修补。
- **schema 兼容红线**：会改变会话 / 配置存储结构的自我修改，必须人工评审，不进自动流水线。
- **Supervisor 最小化**：它只做指针与进程管理，不含业务逻辑，更新走人工。
- **防劣化**：`history.json` 记录每次切换对应的 git commit，连续两次切换后回滚时，自动在会话中提示"该改动方向可能有问题，建议人工介入"。

## 7. 风险与开放问题

1. **macOS 授权路径问题**（§4 Phase 3 表格）：若槽位方案导致 bundle 路径变化，Accessibility 等授权会反复弹窗。需要在 Phase 2 实施前先验证"固定路径 + 内容替换"是否满足签名 / 公证要求。
2. **构建时长**：完整 Electron 构建较慢，"对话中等待构建"体验差。缓解：渲染层改动优先走 dev 热更新；安装版构建放后台，完成后通知。
3. **双窗口困惑**：共存窗口内用户可能对着旧窗口说话。缓解：B 启动时窗口标题带"新版本候选"标识，切换完成后 A 自动退出。
4. **Agent 改坏验证门禁本身**：例如把 typecheck 配置改松。缓解：门禁脚本与配置纳入"保护清单"，Agent 修改这些文件时强制人工确认。

## 9. 打包版本地自进化：渲染层覆盖目录（2026-07-30 决策）

### 9.1 背景：开发版与打包版的本质差异

main.mjs 的加载逻辑决定了自进化的作用域：

```js
const indexPath = app.isPackaged ? packagedIndexPath : devIndexPath;
// 打包版：process.resourcesPath/app-dist/（编译时封进 .app 的死文件）
// 开发版：apps/app/dist/（活的工作区文件）
```

M1 / worktree / 候选实例整套机制之所以"改完刷新即生效"，是因为日常运行的是开发版，应用读的是活文件。打包版读的是包内快照，改磁盘源码零效果。

### 9.2 硬约束：macOS 签名

打包版本地自进化的唯一硬墙不是网络/云端，是签名：**改动 .app 包内任何文件 → 签名失效 → Gatekeeper 拦截**。因此原则定为：**包一个都不动，改动全部落在包外用户目录**。

### 9.3 决策：打包版只做渲染层覆盖目录，底层不可变是特性

打包时在应用里埋"优先读包外覆盖目录"的加载逻辑，自进化产物写入用户目录即可本地生效，不碰包不碰签名。

| 层 | 可进化性 | 理由 |
|----|---------|------|
| 渲染层（界面/页面/交互） | **可进化**（覆盖目录） | 改坏了删目录即回滚，摔不坏 |
| 服务端逻辑（数据/账号/扣费） | 不可变 | 涉及资金与数据完整性 |
| 主进程引导器与覆盖加载器 | **永不可变** | 回滚开关本身；能改它就能破坏恢复路径 |

设计哲学与 M1 保护清单一致：**守门员不参与比赛**——回滚机制必须在自进化够不着的地方。用户得到的不是"阉割版"，而是"摔不坏的版本"。

### 9.4 待解：本地构建能力

打包用户机器上没有 node/pnpm/vite，改完谁来构建？两个候选方向（实施前再定）：

1. **运行时补丁模块**（倾向）：自进化不改主代码，产出小 JS 补丁模块丢进覆盖目录，运行时挂载，**免构建**、零本地依赖。
2. **内嵌精简构建器**：打包内置 esbuild 级构建器（约 10MB），只重建变化模块。

### 9.5 与 M1 的关系

同一套版本管理与安全语义（快照/回滚/版本库/worktree/候选实例），只是目标从 `vendor` 源码树变为用户目录覆盖层。M1 = 开发态形态；本节 = 打包版形态。打包版实施独立排期，当前不阻塞 M2/M3。
